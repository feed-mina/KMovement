# K-Ride AI 여행봇: Advanced RAG 시스템 아키텍처 가이드

K-Ride AI 여행봇은 현재 **Graph RAG를 사용하지 않으며**, 대신 빠르고 정확한 응답을 위해 **Advanced RAG(검색 증강 생성) 기법**과 **LLM(대형 언어 모델)**을 활용하고 있습니다. 

아래는 K-Ride 챗봇의 코어 엔진(`chatbot_chain.py`, `multi_query.py`, `config.py`)에서 실제로 구현된 시스템의 상세 동작 원리와 설정값, 그리고 향후 Graph RAG 도입 시나리오에 대한 안내입니다.

---

## 1. Multi-Query (다중 쿼리 질문 확장)
사용자의 짧거나 모호한 질문 하나만으로는 DB에서 정확한 문서를 찾기 어려울 수 있습니다. 이를 해결하기 위해 LLM을 사용하여 질문을 여러 개로 확장합니다.
- **방식**: Groq LLM API(`openai/gpt-oss-120b` 등의 오픈소스 모델)를 호출하여 사용자의 원본 질문을 **3개의 다른 표현(변형)**으로 바꾸어 달라고 요청합니다. 
- **결과**: `[원본 질문] + [변형 1, 변형 2, 변형 3]` 으로 **총 4개의 쿼리**가 생성됩니다.

## 2. Multi-Source Retrieval (다중 소스 임베딩 및 검색)
생성된 4개의 쿼리는 벡터로 변환되어 여러 데이터베이스를 동시에 찔러 관련 정보를 가져옵니다.
- **임베딩 방식 & TorchServe 통신**: 
  - 생성된 4개의 텍스트 쿼리는 HTTP POST 요청으로 `http://localhost:8085/predictions/embedder` (TorchServe 인퍼런스 서버)로 전송됩니다.
  - 서버에서는 `intfloat/multilingual-e5-small` 모델(다국어 지원, 384차원)을 사용하여 텍스트를 실수형 벡터(Vector) 배열로 반환합니다.
- **ChromaDB 다중 검색 & K값 (Top-K)**:
  임베딩된 4개의 벡터는 총 5개의 컬렉션(DB)에 각각 검색됩니다.
  - **PDF 컬렉션 (가이드북 등)**: 쿼리당 **K=10**개 추출 (`RETRIEVE_TOP_K_PDF`)
  - **POI 컬렉션 4개 (K-Culture, 음식, 자연, 역사)**: 쿼리당 **K=5**개 추출 (`RETRIEVE_TOP_K_POI`)
  - 검색된 결과들은 `Metadata`(문서 고유 ID, 장소명) 기준으로 중복 제거(Deduplication)를 거쳐 하나의 거대한 후보군 풀(Pool)로 합쳐집니다.

## 3. Reranker (문서 재정렬 및 점수 부여)
위 단계에서 수집된 수십 개의 문서는 단순한 벡터 유사도로 뽑힌 것이므로 정확도가 떨어질 수 있습니다. 이를 해결하기 위해 리랭커(Reranker) 모델이 개입합니다.
- **채점 방식 & TorchServe 통신**: 
  - 후보군 텍스트들과 사용자의 '원본 질문'을 쌍(Pair)으로 묶어 `http://localhost:8085/predictions/reranker`로 전송합니다.
  - 리랭커 모델(`cross-encoder/ms-marco-MiniLM-L-6-v2`)이 두 문장 사이의 실제 의미적 연관성을 0~1 사이의 확률값(또는 로짓) 실수형 **점수(Score)**로 평가하여 반환합니다. 
  - *참고: 현재 시스템에 별도의 소스별(가중치) 로직은 없으며, 순수하게 크로스-인코더 딥러닝 모델이 판단한 연관성 점수로만 정렬됩니다.*
- **최종 K값 (Top-K)**:
  - 점수가 높은 순으로 내림차순 정렬한 뒤, 최종적으로 **가장 높은 K=10개**(`RERANK_TOP_K`)의 문서만 살아남습니다.

## 4. Context 조립 (프롬프트 구성)
최종 선발된 10개의 문서를 바탕으로 LLM에게 줄 컨텍스트(참고 자료)를 조립합니다.
- **조립 방식**: 
  - 10개의 문서를 순서대로 `[1] (내용)`, `[2] (내용)` 형태로 문자열로 이어 붙입니다.
  - 이때 내용이 너무 길면 토큰 제한을 막기 위해 **최대 500자**씩만 잘라서(Truncate) 사용합니다.
  - 각 문서의 메타데이터에서 **POI 정보**(장소명, 주소, 위도, 경도)와 **출처**(PDF 파일명)를 별도의 JSON 리스트로 추출합니다. 이 데이터는 프롬프트에 들어가지 않고, 화면(UI)에 마커를 찍거나 카드형태로 보여주기 위해 응답 데이터에 함께 반환됩니다.

## 5. LLM 응답 생성 (Groq) 및 대화 이력 (N턴)
조립된 프롬프트와 사용자의 대화 기록을 LLM에 던져 최종 답변을 생성합니다.
- **N (대화 이력)**: 
  - 현재 설정된 **N은 10** (`MAX_HISTORY_TURNS = 10`) 입니다. 
  - 즉, 사용자가 과거에 묻고 봇이 답했던 **가장 최근의 10번의 왕복 대화(총 20개 메시지)**를 메모리에서 꺼내 함께 전달합니다. 이를 통해 맥락이 끊기지 않는 대화가 가능합니다.
- **최종 생성**: Groq API에 시스템 프롬프트(지시사항), 대화 이력 20개, 그리고 `[참고 자료]` 및 `[사용자 질문]`을 넣어 호출하며, 모델이 자연스러운 한국어로 최종 답변을 작성합니다.

### Graph RAG 향후 확장 시나리오
현재의 벡터 기반 검색은 "의미상 비슷한 글"을 찾는 데는 강하지만, **"A 장소 근처의 B 카테고리 장소"**나 **"특정 시대의 역사가 얽힌 장소들"** 같은 복잡한 관계 추론에는 약합니다. 향후 추가 확장 방향:

1. **Entity 추출 기반 그래프 검색**: 챗봇 질문에서 개체(예: "강남역", "카페")를 추출 → 그래프 탐색
2. **통합 리랭킹**: 벡터 DB 문서 + 그래프 관계 요약 텍스트를 함께 리랭커에 넣어 점수 매기기
3. **LLM 컨텍스트 강화**: 관계 정보(Graph) + 텍스트 묘사(Vector)를 동시 참고하여 입체적 답변
