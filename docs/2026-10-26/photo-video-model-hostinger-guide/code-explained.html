1. 이 보고서를 읽는 방법

구분 내용
독자 코드 문법을 몰라도 사진 한 장이 어떻게 영상이 되는지 이해하려는 사람. 유지보수 담당자는 옆의 함수명으로 실제 소스를 찾을 수 있다.
설명 기준 앞선 보고서와 같은 KMovement 소스 ce257f437fd7f91aff4a80badb10f1b3917ac6f8. 해당 버전의 실제 함수를 다시 읽었다.
현재 구현 개인 사진 업로드·작업 기록·FFmpeg 생성·본인 영상 조회, 기존 커뮤니티 Runpod 요청과 Cloudinary 전달.
앞으로의 제안 영상 전용 연결 주소, 개인 AI 모델 실행 기록, 결과 회수, 새 모델 연결. 해당 부분마다 “제안”이라고 표시한다.
설명용 사례 사용자 101번이 여행 사진 한 장을 올린다는 가상 사례. 사진 P·요청 R·작업 J는 읽기 위한 별칭이며 실제 프로그램에는 긴 식별 번호를 넣는다.
산출 범위 문서 작성·표시 검수·GitHub 게시. 실제 서버·DB·영상 생성 코드는 변경하지 않았다.

API(Application Programming Interface)는 프로그램의 요청·응답 창구다. DB(Database)는 기록을 보관하는 데이터베이스다. CPU(Central Processing Unit)는 일반 계산 장치이고, GPU(Graphics Processing Unit)는 영상 모델의 큰 계산에 사용하는 장치다. “반환값”은 함수가 호출한 곳에 돌려주는 값이고, “저장·변경 효과”는 파일이나 기록에 남기는 변화다.

2. 처음에는 네 가지 역할만 기억한다

사용자는 한 화면에서 사진을 고르고 결과를 보지만, 서버 안에서는 여러 담당자가 일을 나눈다.

쉬운 역할 실제 담당 하는 일
화면 담당 Next.js의 TravelVideoPage, VideoCreator, VideoWorkspace 사진 미리보기·버튼·작업 상태·재생 화면을 보여준다.
신원 확인과 중계 담당 Next 서버의 proxy() Spring에 로그인 사용자를 확인하고 개인 영상 서버로 요청을 전달한다.
기록 담당 개인 app.py와 database.py 사진 주인·작업·처리 상태·코스 설명을 SQLite에 기록한다.
영상 작업자 개인 worker.py 대기 중인 작업을 가져와 사진을 움직이는 MP4 파일을 만든다.

기존 커뮤니티 AI 영상에는 Spring AnimationService, 미디어 게이트웨이, Runpod GPU 작업자가 추가로 등장한다. 현재 개인 영상 작업자가 Runpod 작업자를 호출하는 연결은 없다.

“웹사이트가 켜짐”, “작업이 접수됨”, “GPU 생성이 끝남”, “파일을 재생할 수 있음”은 각각 다른 단계의 결과다.

3. 화면에서 사진을 고르는 일과 서버에 올리는 일

현재 구현. VideoCreator는 사용자가 파일을 고르면 먼저 브라우저 안에서 미리보기를 만든다. 파일이 JPEG·PNG·WebP인지, 크기가 한도를 넘지 않는지 화면에서도 확인한다. 이때 미리보기가 보인다는 사실만으로 서버 저장이 끝난 것은 아니다.

“사진 올리기”를 눌러야 사진 데이터가 서버로 전송된다. 서버가 사진 번호를 돌려주면 화면은 그 번호를 기억하고 “사진을 저장했습니다”를 표시한다. 그다음 “영상 만들기”를 누르면 사진 파일 전체가 아니라 저장된 사진 번호와 요청 번호를 보낸다.

사용자 행동 화면 내부 처리 받는 결과·보이는 변화
사진 선택 파일 형식·크기 확인, 브라우저 임시 미리보기 생성 선택 사진 표시. 아직 서버 사진 번호 없음
사진 올리기 submit('upload')가 사진 바이트를 전송 photoId 저장, 저장 안내·영상 만들기 버튼 표시
영상 만들기 submit('generate')가 photoId와 requestId 전송 작업 응답을 onCreated()로 넘김
다른 사진 선택 이전 photoId·요청 번호를 지우고 새 사진 선택 이전 번호로 새 사진 작업을 요청하는 혼동 방지

submit()은 화면 상태를 바꾸고 요청을 보내는 함수다. 별도의 업무 결과 객체를 직접 반환하도록 작성된 함수는 아니다. 생성 결과는 onCreated()라는 전달 함수로 다음 화면 처리에 넘긴다. 요청 중 버튼을 막고 진행 상태를 표시하는 것은 중복 클릭을 줄이기 위한 화면 처리다.

관련 코드: VideoCreator와 VideoWorkspace. 미리보기의 임시 주소는 브라우저 안에서 사용하는 주소이며 Runpod가 내려받을 외부 사진 주소가 아니다.

코드에 근거한 과정 설명도 · 실제 작업 실행 아님

VideoCreator가 선택 파일을 검사하고 미리보기를 만듭니다. 이 단계에서는 서버의 사진 번호가 생기지 않습니다.

4. 서버는 사진을 받기 전에 로그인부터 확인한다

현재 구현. 브라우저가 개인 영상 서버를 직접 지시하지 않고 Next의 중계 함수 proxy()를 거친다.

F1에서 기능이 켜져 있는지 확인한다. F2에서 Spring의 /api/auth/me에 현재 쿠키를 보내 “누가 로그인했는지” 묻는다. F3에서 로그인한 사용자 번호가 정상인지 확인하고 내부 요청의 소유자 번호를 만든다. F4에서 개인 영상 API가 내부 키와 소유자 번호를 검사한다.

단계 자연어로 풀어 쓴 코드 실제 확인 위치
F1 “이 기능을 사용할 수 있는 상태인지, 연결 주소·키가 있는지 먼저 확인해 주세요.” PHOTO_VIDEO_ENABLED와 연결 설정 검사
F2 “이 쿠키로 로그인한 사람이 누구인지 로그인 서버에 확인해 주세요.” /api/auth/me 요청
F3 “로그인 서버가 확인한 사용자 번호를 내부 편지에 붙여 주세요.” X-Photo-Video-Owner 생성
F4 “내부 키가 맞고 사용자 번호가 올바를 때만 처리해 주세요.” 개인 API의 owner()

개인 API의 owner()는 검사를 통과하면 정수 사용자 번호를 반환한다. 예를 들어 설명용 사용자 101이면 이후 사진·작업 조회에 101이 사용된다. 브라우저에서 owner를 202로 바꿔 보내 다른 사람으로 행동하게 하는 구조로 만들지 않는다.

사진 올리기·작업 만들기 같은 쓰기 요청은 실제 사이트에서 온 요청인지도 검사한다. 코스가 연결되어 있으면 코스 검증이 중간에 추가되고, 코스가 없으면 이 검증을 생략한다. 영상 데이터 응답은 바이트 흐름으로 전달할 수 있으므로 모든 응답을 JSON으로 읽는 것은 아니다.

관련 코드: Next proxy(), 개인 owner(). 개인 API가 내부 헤더를 신뢰할 수 있도록 서비스 접근 범위와 내부 키를 관리해야 한다.

5. 사진 서버는 파일을 다시 읽고 저장한다

현재 구현. 개인 API의 upload()는 파일 이름이나 브라우저가 알려준 형식만 믿고 저장하지 않는다. 데이터를 받으면서 크기를 확인하고, 실제 이미지로 열어 읽을 수 있는지 검사한다.

사진 방향 정보를 반영해 바로 세운 뒤 RGB 색상으로 바꾸고, 가로·세로가 1920 범위에 들어오도록 비율을 유지해 줄인다. 다시 JPEG로 저장하면서 원래 파일 이름과 EXIF 촬영 위치 같은 부가정보를 보존하지 않는다.

검사를 통과하면 새 photoId를 만든다. 저장 폴더에는 그 번호를 이름으로 한 JPEG를 쓰고, SQLite의 photos에는 사진 번호·주인·등록 시각을 남긴다. 응답에는 photoId를 돌려준다.

실제 코드 동작 쉬운 의미
형식·크기·이미지 디코딩 검사 “다룰 수 있는 진짜 사진인지 확인한다.”
exif_transpose와 RGB 변환 “방향을 맞추고 다룰 색상 방식으로 통일한다.”
thumbnail과 JPEG 재저장 “비율을 유지해 크기를 제한하고 새 사진 파일로 만든다.”
파일 저장 + photos 기록 “사진 내용과 주인 정보를 각자 맞는 곳에 남긴다.”
photoId 응답 “이후 이 사진을 찾을 번호를 화면에 알려준다.”

사용자별 사진 보관 한도는 코드상 20장이다. 한도를 넘으면 429 응답을 준다. 저장 과정에서 예외가 발생하면 해당 시도에서 만든 파일을 지우는 정리 처리가 있다. DB 트랜잭션만으로 파일 저장까지 하나의 완전한 거래가 되는 것은 아니다.

설명용 사례: 사진 P의 파일 내용은 P.jpg에 있고, P가 사용자 101의 사진이라는 정보는 photos에 있다. SQLite 안에 JPEG 전체를 넣는 방식은 아니다.

관련 코드: upload().

6. 사진 번호·요청 번호·작업 번호는 서로 다르다

UUID(Universally Unique Identifier)는 서로 겹칠 가능성을 매우 낮게 만든 식별 번호 형식이다. 실제 개인 사진과 작업에는 긴 UUID를 사용한다. 아래 P·R·J는 설명용 별칭이다.

번호 쉬운 뜻 생기는 시점 쓰는 곳
photoId / P 어떤 사진인가 사진 업로드 성공 저장된 사진 조회·생성 입력 연결
requestId / R 같은 요청을 다시 보낸 것인가 화면에서 생성 요청을 준비할 때 중복 접수 확인
jobId / J 어떤 개인 영상 작업인가 서버에서 새 작업 생성 상태·이력·재시도·영상 재생
Runpod 작업 번호 외부 GPU의 어떤 작업인가 외부 제출 성공 기존 AI 경로의 외부 상태 조회

사진 P 하나로 여러 작업을 만들 수 있다. 반대로 같은 요청 R을 네트워크 문제로 다시 보내는 것은 새 영상 네 개를 만들려는 뜻이 아닐 수 있다.

현재 개인 경로에는 Runpod 작업 번호가 생기지 않는다. 앞으로 AI를 연결할 때 개인 J와 외부 작업 번호를 함께 기록해야 하며 두 번호를 같은 값으로 취급하면 안 된다.

7. “영상 만들기”는 먼저 대기표를 만드는 일이다

현재 구현. 개인 API의 enqueue()는 작업 접수 담당이다. 사진을 바로 영상으로 바꾸는 함수가 아니다.

먼저 사용자 101과 요청 R로 기존 작업이 있는지 찾는다. 같은 요청에 같은 사진·같은 재시도 원본·같은 코스 설명이 들어오면 기존 작업을 돌려준다. 같은 요청 번호에 다른 내용을 넣으면 409로 거절한다.

새 요청이면 본인 사진인지, 현재 진행·대기 작업이 2개 미만인지, 한국 날짜 기준 하루 작업 수가 10개 미만인지 확인한다. 통과하면 작업 J를 만들고 대기 상태로 기록한 뒤 작업 응답을 돌려준다.

판단 순서 자연어 규칙 결과
중복 요청 확인 “이 사람이 이 요청 번호로 이미 접수했는가?” 같은 내용이면 기존 작업 응답
내용 충돌 확인 “같은 번호인데 사진·원본·코스가 바뀌었는가?” 409
소유권 확인 “요청한 사진이 이 사람의 사진인가?” 없으면 404
사용량 확인 “동시 작업과 오늘 요청 한도 안인가?” 넘으면 429
새 작업 저장 “새 번호를 붙여 대기줄에 넣는다.” 작업 응답. 생성 API는 202 접수 상태 사용

enqueue()의 반환값은 job_response()가 만든 작업 정보다. 별도로 SQLite에 새 행을 남기는 효과가 있다. 같은 요청을 되돌려주는 경우에는 새 행을 만들지 않는다.

사진·주인·요청·원본·코스처럼 연결 의미를 정하는 값은 이미 생성한 작업에서 마음대로 바꾸지 못하도록 DB 규칙도 둔다.

관련 코드: enqueue()와 job_response(), DB 규칙.

8. 영상 작업자는 대기줄에서 한 건을 가져온다

현재 구현. worker.py의 run_once()는 “대기 중인 작업 하나를 처리해 보세요”라는 뜻이다.

DB가 없거나 대기 작업이 없으면 False를 돌려준다. 대기 작업이 있으면 오래된 순서대로 하나를 선택하고 진행 중으로 바꾼 뒤 파일 생성 함수를 실행한다. 이때 DB의 쓰기 거래를 먼저 확보해 작업을 고르는 과정을 보호한다. 생성 중 내내 DB 잠금을 유지하는 구조는 아니다.

생성이 끝나면 성공·실패·오류 종류·처리 시간을 기록한다. run_once()는 영상 생성에 실패했더라도 한 건을 처리했다면 True를 돌려준다. 이 True는 “영상이 성공했다”가 아니라 “이번에 처리한 일이 있었다”는 뜻이다.

코드에서 보이는 것 자연어 의미
QUEUED 순서를 기다리는 작업
RUNNING 작업자가 가져가 처리 중인 작업
COMPLETED 파일 생성을 마치고 완료로 기록한 작업
FAILED 이번 시도에서 실패로 기록한 작업
render_ms 이 함수에서 측정한 처리 경과 시간. 단위는 밀리초

반복 함수 main()은 일이 없거나 처리 가능한 DB 오류가 발생하면 약 2초 뒤 다시 확인한다. 진행 중으로 남은 지 10분이 넘은 작업을 중단 실패로 정리하는 처리도 있다. 이는 현재 CPU 작업 기준이다. 장시간 GPU 모델을 추가하면서 같은 기준을 그대로 쓰면 아직 생성 중인 작업을 실패로 판단할 수 있어 별도 설계가 필요하다.

관련 코드: run_once()와 main().

9. 사진을 움직이는 MP4로 만드는 함수를 읽는다

현재 구현. render_photo(source, target)의 두 입력은 “읽을 사진 파일 위치”와 “완성 영상을 둘 위치”다. 이 함수는 학습 모델을 실행하지 않고 FFmpeg라는 미디어 처리 프로그램을 실행한다.

사진 한 장을 여러 프레임에 사용하고, 화면 크기를 맞춘 뒤 천천히 확대해 움직임을 만든다. 최종 설정은 1280×720, 초당 25프레임, 총 125프레임이다. 길이는 약 5초이고 소리는 넣지 않는다.

처음에는 완성 파일과 구분되는 임시 MP4를 만든다. FFmpeg 실행이 끝나면 ffprobe로 정보를 읽고 H.264 영상이며 길이가 4.8~5.2초 범위인지 명시적으로 확인한다. 출력 설정으로 해상도를 지정하지만 이 확인 조건이 해상도까지 다시 비교하는 것은 아니다. 검사를 통과하면 임시 파일을 최종 이름으로 바꾼다.

단계 자연어 해석 파일에 남는 결과
사진 반복 입력 “한 장의 사진을 영상 프레임 재료로 계속 사용한다.” 여러 시점의 프레임
크기 맞춤·여백 “비율을 지키며 목표 화면 안에 넣는다.” 1280×720 출력 설정
확대 “프레임이 바뀔 때 사진을 조금씩 크게 보여준다.” 카메라가 다가가는 듯한 효과
임시 파일 생성 “아직 검사 전인 결과를 완성 파일과 구분한다.” 임시 MP4
형식·길이 확인 “재생 가능한 예상 형식·길이인지 확인한다.” 통과한 파일만 최종 이름 사용

이 함수의 반환값은 None이다. 즉, 완성 영상 바이트를 함수 호출자에게 직접 반환하지 않는다. 지정된 위치에 MP4 파일을 만드는 것이 이 함수의 결과 효과다. 실행 시간이 제한을 넘거나 실행에 실패하면 예외가 나고, 호출한 run_once()가 실패 종류를 기록한다.

관련 코드: render_photo().

10. 완성 상태를 보여주는 일과 영상을 보내는 일

현재 구현. job_response()는 DB의 한 행을 화면이 읽기 쉬운 정보 묶음으로 바꾼다. 예를 들어 “사진 P로 만든 작업 J가 완료되었고, 재생은 이 주소로 요청하면 된다”는 내용을 구성한다.

응답 이름 쉬운 의미 화면 연결
jobId·photoId 작업 번호·원본 사진 번호 선택 작업·원본 연결
status 대기·진행·완료·실패 작업 상태 문구
renderMilliseconds 작업자가 측정한 처리 시간 처리 정보
retryOf 어느 실패 작업을 다시 시도했는가 원본과 새 시도 연결
trip 저장된 코스 설명을 다시 객체로 푼 값 연결 장소 표시
videoUrl 완료 작업의 보호된 재생 요청 주소 video 요소·다운로드 링크
methodLabel 사진 확대·이동 방식이라는 설명 결과 방식 안내

videoUrl은 현재 DB에 저장한 Cloudinary 주소를 꺼내는 값이 아니다. 작업 번호를 사용해 보호된 재생 경로를 만드는 값이다.

그 주소로 실제 재생을 요청하면 video()가 “로그인한 사용자의 작업인가”, “완료 상태인가”, “MP4가 실제 존재하는가”를 다시 확인한다. 소유한 작업이 없으면 404, 아직 준비되지 않았으면 409를 응답한다. 준비됐으면 JSON이 아닌 영상 파일을 돌려준다.

status()는 작업 한 개의 정보, history()는 본인의 작업 목록을 조회한다. 목록은 새 기록부터 한 페이지 20개씩이다. 화면에 그려진 완료 표시만으로 파일 존재 확인을 대신하지 않는다.

현재 비용 응답의 외부 모델 사용료 0은 FFmpeg 경로의 외부 생성 모델 비용을 뜻한다. 서버·저장·전송 비용은 미산정이다. AI 연결 후에도 이 값을 무조건 0으로 두면 안 된다.

관련 코드: job_response(), status(), history(), video(), 재생 화면.

11. 사진·작업·파일을 별도로 보관하는 이유

SQLite는 하나의 파일에 DB를 담아 사용하는 도구다. 개인 영상 저장소에는 두 가지 장부와 실제 파일이 있다.

보관 대상 기록하는 내용 보관하지 않는 내용
photos 사진 번호·주인·등록 시각 JPEG 전체
jobs 작업 번호·사진 번호·주인·상태·요청·재시도·처리 시간·코스 설명 MP4 전체
사진 파일 다시 저장한 JPEG 내용 로그인 계정 정보
영상 파일 생성된 MP4 내용 작업 이력 전체

사진과 작업의 연결은 “사진 번호만 같다”로 검사하지 않는다. 사진 번호와 주인이 함께 일치해야 한다. 재시도도 원본 작업 번호·주인·사진 번호가 함께 맞아야 한다.

이 그림의 연결은 SQLite에 정의된 실제 복합 외래키다. FK(Foreign Key, 외래키)는 연결 대상이 실제 존재하는지 DB가 검사하는 규칙이다. owner가 Spring 사용자 번호와 의미를 공유해도 SQLite가 PostgreSQL 사용자 테이블을 직접 외래키로 검사하는 것은 아니다.

connect()는 DB를 열 때마다 외래키 검사를 켠다. initialize_schema()는 DB 구조를 준비하고, 기존 형식에서 이전할 때 백업·검증 절차를 사용한다. 잘못된 연결을 발견했다고 행을 임의로 삭제해 맞추는 방식은 아니다.

사진·작업·완료 파일이 서로 맞아야 서비스를 복구할 수 있으므로 백업할 때도 DB와 JPEG·MP4를 같은 기준 시점으로 보존한다.

관련 코드: database.py.

12. 재시도와 trip_json을 쉬운 말로 읽는다

실패한 작업은 새 시도로 남긴다

현재 구현. retry()는 실패 작업을 다시 시도할 때 사용한다. 원본 사진과 코스 설명을 읽어 새 작업을 만들고 “어느 작업에서 다시 시작했는지” 기록한다. 원본을 성공 작업으로 덮어쓰지 않는다.

본인의 실패 작업이어야 하며, 같은 원본의 대기·진행·완료 재시도가 이미 있으면 추가 재시도를 막는다. 이미 만들어진 원본 연결도 함부로 바꾸지 못하게 한다.

설명용으로 실패한 J를 다시 시도하면 새 작업 J2가 생기고 J2의 retryOf가 J를 가리킨다. 화면은 새 작업 J2의 상태를 보게 된다. 재시도 요청 자체도 새로운 requestId로 중복을 확인한다.

코스 설명은 사진 옆에 붙인 메모다

trip_json은 검증된 코스의 선택 장소 정보를 문자로 보관한 값이다. JSON(JavaScript Object Notation)은 이름과 값의 짝으로 정보를 담는 형식이다.

사진을 코스에서 연결해 왔다면 Next가 코스 검증 API에 묻고, 그 결과를 trip으로 개인 API에 넘긴다. 개인 API는 이를 정해진 순서의 JSON 문자열로 만들어 jobs.trip_json에 저장한다. 조회할 때는 다시 정보 묶음으로 풀어 trip으로 반환한다. 코스 연결이 없으면 저장값은 비어 있다.

코드 이름 자연어 의미
itineraryId 코스 발급을 구분하는 번호
poiId 선택한 장소 번호
placeName·placeAddress 검증 API가 돌려준 장소 이름·주소
catalogRevision 기준 장소 자료의 버전을 구분하는 값
contextIssuedAt 코스 자료 확인 맥락의 발급 시각
notice 이 연결의 의미와 한계를 설명하는 안내

trip_json은 사진의 실제 촬영 위치를 판정한 결과가 아니다. 현재 CPU 작업자는 이 메모를 읽어 장소에 맞는 장면을 생성하지 않는다. 재시도는 저장된 메모를 복사하며 최신 코스로 다시 검증하는 절차는 포함하지 않는다.

관련 코드: retry()와 TripContext, 코스 검증을 거치는 proxy().

13. 기존 커뮤니티 AI 요청은 다른 길로 이동한다

현재 구현. 기존 커뮤니티의 AI 생성 요청은 Spring AnimationService가 담당한다. 본인 게시글·허용 입력 등을 확인한 뒤 사진 주소와 작업 종류를 미디어 게이트웨이에 보낸다.

게이트웨이는 실제 모델을 직접 계산하는 대신 Runpod에 작업을 접수한다. 외부 작업 번호가 돌아오면 Spring이 그 번호와 대기 상태를 PostgreSQL에 기록한다. 이후 상태 조회가 외부 결과를 가져와 작업을 갱신한다.

담당 자연어로 설명한 입력·처리·출력
AnimationService 게시글·작업 종류를 받아 요청을 만들고, 외부 접수 번호가 있으면 작업 기록을 저장해 돌려준다.
runpod_proxy() 작업 종류에 맞는 실행 창구를 고르고, Runpod에 접수한 응답을 돌려준다.
runpod_status() 외부 작업 번호로 현재 설정된 실행 창구들을 조회하고 찾은 상태 응답을 돌려준다.
GPU handler() 작업 내용을 받아 지원 여부를 확인하고 해당 생성 함수를 실행해 결과 정보를 돌려준다.
applyRunPodStatus() 조회한 상태를 읽어 작업 객체의 상태·결과 주소·실제 모델 정보를 갱신한다. 별도 반환값은 없다.

접수 번호가 없거나 요청 중 예외가 나면 현재 Spring 코드는 실패 작업을 저장한다. 이 사실만으로 “외부에서 실행이 절대 시작되지 않았다”까지 증명되는 것은 아니다. 앞선 보고서의 제출 불명 상태는 이 빈틈을 보강하자는 새 제안이다.

관련 코드: AnimationService, 미디어 게이트웨이, GPU handler().

14. 제출 주소·조회 주소·작업 종류를 구분한다

엔드포인트는 작업을 받을 실행 창구다. route는 그 창구에 요청할 일의 종류다. 택배로 비유하면 endpoint는 물류센터, route는 그 안에서 처리할 서비스 종류에 가깝다.

코드·주소 자연어 해석
POST /v2/{endpoint}/run “이 실행 창구에 새 작업을 맡겨 주세요.”
GET /v2/{endpoint}/status/{job_id} “앞서 맡긴 작업 번호의 상태를 알려 주세요.”
route=tora_cogvideox_i2v “궤적 제어를 사용하는 Tora 영상 작업을 요청합니다.”
RUNPOD_TORA_ENDPOINT_ID 단일 Tora 작업을 보낼 창구 번호
RUNPOD_MEDIA_ENDPOINT_ID 일반 미디어·배치 작업을 보낼 창구 번호
RUNPOD_ENDPOINT_ID 전용 설정이 비었을 때 사용하는 기존 대체 창구 번호

제출 응답은 완료 MP4가 아니라 접수 번호와 현재 상태일 수 있다. 같은 번호로 상태를 확인하는 요청은 새 생성 요청과 구분한다.

현재 단일 Tora는 전용 창구를 고르지만 배치는 항상 미디어 창구로 간다. 배치 안의 photo_route를 Tora로 골라도 전용 창구로 자동 재전송하지 않는다. 창구 번호를 고르는 코드와 창구 안에서 모델을 고르는 코드는 별개이기 때문이다.

상태 조회는 현재 설정된 여러 창구를 탐색한다. 새 설계에서는 제출 시점의 공급자·창구·작업 번호를 함께 남겨 나중에 설정이 바뀌어도 원래 작업을 찾게 한다.

관련 코드: _runpod_endpoint_for_route(), runpod_proxy(), runpod_status(), runpod_batch_proxy().

15. 생성된 파일·업로드 주소·DB 저장은 세 단계다

현재 구현. GPU에서 MP4가 생성되면 finalize_result()가 최종 영상 파일 항목을 찾는다. 파일이 존재하면 Cloudinary에 올리고 성공 주소를 결과의 result_url 등에 넣는다.

이 함수는 PostgreSQL에 직접 저장하지 않는다. Runpod 결과를 받은 Spring이 응답을 해석해 작업 객체의 resultUrl을 설정하고 저장 경로에서 보존한다. 결과 주소가 없는 완료 응답을 Spring이 유효한 성공으로 받아들이는지도 별도 파서에서 판단한다.

단계 쉬운 설명 확인할 결과
파일 생성 GPU 작업자 안에 영상 파일이 만들어짐 파일 생성 성공 여부
외부 보관 결과 전달 함수가 Cloudinary 업로드 시도 업로드 성공·result_url
서비스 기록 Spring이 외부 응답을 조회·파싱해 보존 커뮤니티 작업 상태·result_url

“외부 작업 완료”와 “우리 서비스에서 재생 가능한 완료”를 구분해야 하는 이유다. 개인 영상은 현재 보호된 로컬 파일을 제공한다. 개인 사진 AI 기능을 추가할 때 기존 공개 URL 전달을 그대로 사용하기보다 비공개 결과 회수와 본인 재생 연결을 설계한다.

관련 코드: finalize_result(), applyRunPodStatus().

코드 조각 자연어 해석
@Value “애플리케이션 설정에서 값을 읽어 이 자리로 넣어 주세요.”
kride.media.url 새로 만들 영상 전용 연결 주소 설정

주소를 설정하는 것 자체가 서버를 옮기거나 모델을 실행하는 것은 아니다. 그 주소에 실제 중계 서비스가 떠 있고 서로 연결돼야 한다. 기본 주소 설정과 실제 요청 전송도 다른 시점이다.

영상 전용 설정을 제안한 이유는 코스·채팅의 목적지와 영상 중계의 목적지를 따로 바꿀 수 있게 하기 위해서다. Hostinger CPU 앱에는 현재 영상 제출 경로가 없으므로 같은 주소로 맞추는 것만으로 연결이 끝나지 않는다.

17. Docker 구성 예제를 운영 지시문으로 읽는다

앞선 보고서의 제안 구성 해설. 완성 배포 파일이 아니다.

Docker 컨테이너는 프로그램과 실행 환경을 묶어 띄운 단위다. Compose는 어떤 컨테이너를 어떤 설정으로 연결할지 적는 구성 문서다.

구성 이름 쉬운 뜻 이 보고서의 예시가 지시하는 일
services 실행할 프로그램 목록 media-gateway라는 중계 프로그램을 준비
image 실행할 프로그램 묶음 검토한 이미지와 digest 사용
environment 프로그램에 전달할 설정 내부 키·Runpod 키·실행 창구 번호 전달
expose 컨테이너의 서비스 포트 정보 7860에서 서비스하도록 구성. 이것만으로 호스트 공개 포트를 만드는 것은 아님
networks 서로 통신할 연결망 Spring이 연결된 Docker 네트워크에 참여
restart: unless-stopped 종료됐을 때 재시작할 정책 명시적으로 중지하지 않은 서비스의 재기동 지원

이미지 digest는 어떤 이미지 내용인지 고정하는 지문에 가깝다. 주소만 바꿔도 새 버전 코드가 생기는 것은 아니므로 어떤 이미지를 실행하는지 함께 확인한다.

예제의 달러 기호와 중괄호는 Compose 실행 환경의 값을 읽으라는 문법이다. 변수 뒤의 물음표가 붙은 검사 표현은 값이 없거나 비었으면 실행 준비 단계에서 오류를 내라는 뜻이다. 설명용 문자열을 비밀번호로 쓰라는 뜻이 아니다.

같은 service 이름을 사용해도 연결망이 다르면 통신하지 못한다. 반대로 expose가 없거나 있다고 해서 네트워크 접근 권한·방화벽이 완성되는 것도 아니다. 내부망·공개 라우터·실제 포트 구성을 함께 확인한다.

KRIDE_MODEL_GENERATION_ENABLED=false는 게이트웨이의 로컬 생성 기능 설정이다. 기존 /jobs/runpod 외부 제출까지 모두 차단하는 스위치로 해석하지 않는다.

제안 원문: 기존 보고서 4장. 현재 게이트웨이: app.py.

19. 새 모델을 추가한다는 말을 개발 작업으로 바꾼다

제안. 모델 선택 버튼을 추가하는 일만으로 새 AI 모델이 연결되지는 않는다. 현재 개인 API는 정해진 입력만 허용하므로 새 model 필드를 그냥 보내면 거절될 수 있다.

사용자 입장에서 원하는 일 개발자가 추가할 일 만들 결과
풍경을 자연스럽게 움직이게 만들기 지원 모델·입력 조건을 정하고 서버에서 허용된 모델로 변환 생성형 영상 작업
사진 속 인물을 춤추게 하기 기준 인물과 승인된 동작을 받고 해당 모델 전용 포즈 전처리 포즈 가이드와 댄스 결과
얼굴 표현 추가 얼굴 추적·후처리·원래 영상으로 합성을 검증 원본과 비교할 선택 결과
카메라로 동작 연습 브라우저 관절 추출·몸 크기와 방향 보정·시간 정렬·유사도 계산 설명 가능한 동작 피드백

어댑터는 우리 서비스의 요청을 각 모델이 알아듣는 형식으로 바꾸고 결과를 다시 공통 형식으로 돌려주는 연결 코드다. 서로 다른 모델이 같은 관절 배열·크기·프레임·출력 형식을 사용하지 않으므로 필요하다.

가중치는 학습된 모델의 숫자 파일, 추론은 그 숫자를 읽어 새 결과를 만드는 실행, 미세학습은 그 숫자의 일부를 목적에 맞게 다시 조정하는 과정이다. 처음에는 기존 가중치로 추론을 연결하고 실제 부족한 점을 확인한다.

모델별 환경을 분리하면 한 모델의 Python·PyTorch 버전 변경이 다른 모델을 함께 망가뜨릴 가능성을 줄일 수 있다. 구체적 후보와 사용 조건은 원래 보고서 6장을 따른다.

21. 개인 사진의 외부 전달과 실패 복구를 풀어 쓴다

앞선 보고서의 새 제안이다.

개인 사진 주소는 본인 로그인으로 보호된다. Runpod는 사용자의 브라우저 쿠키를 갖고 있지 않으므로 그 주소를 전달하는 것만으로 사진을 읽지 못한다. 서버가 동의를 확인한 뒤 특정 사진을 제한된 시간에만 읽는 주소를 발급하는 연결이 필요하다.

서명 주소는 “지금 이 파일에 접근할 수 있다는 제한된 통행증”이다. 긴 주소라고 영구 비공개가 보장되는 것은 아니므로 유효기간·범위·로그 처리·결과 보관을 함께 정한다.

또한 요청을 보냈는데 답변이 끊겼을 때는 외부 생성이 이미 시작됐을 수 있다. 이때 무조건 다시 생성하면 중복 실행·과금이 생길 수 있다.

제안 상태 이름 자연어 의미 다음 행동
SUBMITTING 외부에 접수를 보내는 중 응답 확인
SUBMIT_UNKNOWN 접수 여부를 확실히 모름 기존 제출을 찾고 무조건 새로 보내지 않음
RUNNING 외부 모델이 생성 중 기존 작업 번호로 상태 확인
DELIVERING 생성 결과를 우리 저장소로 가져오는 중 파일과 기록 검증
DELIVERY_RETRY 결과 전달만 다시 필요함 같은 결과를 다시 회수
COMPLETED 내부에서 재생할 준비까지 마침 소유자 확인 후 재생

model_runs는 이런 실행 이력을 따로 기록하자는 테이블 제안이다. 현재 DB에 이미 존재하는 테이블로 설명하지 않는다. 외부 생성 번호·제출 당시 창구·모델 버전·동의·비용과 내부 작업 J를 연결한다. 기존 saved_item을 영상 작업표로 바꾸자는 뜻도 아니다.

22. 화면에서 문제를 발견하면 어디를 읽을지 정한다

보이는 상황 쉬운 해석 먼저 볼 코드

이 표는 실제로 이번에 장애를 재현한 결과가 아니라 코드에 따른 확인 순서다. 서비스 화면에서 본 오류 문구와 서버별 원인을 함께 확인한다.

23. 이 해설의 확인 결과와 사용 범위

실제 함수의 입력·처리·반환과 저장 효과를 대조했다. 특히 “사진 선택과 업로드”, “접수와 생성”, “함수 반환값과 파일 저장”, “외부 완료와 내부 재생”, “현재 구현과 새 제안”을 구분했다.

문서 검수 결과는 별도 기록에 남긴다. 이 문서의 HTML과 Markdown은 같은 본문을 사용한다. 그림은 코드에 근거한 관계·흐름 설명이며 실제 운영 화면 캡처가 아니다. 문서 안의 단계 선택 도구는 설명만 바꾸고 사진 업로드·로그인·영상 생성 요청을 보내지 않는다.

운영 로그인·서버 이전·GPU 생성·DB 마이그레이션은 이번에 실행하지 않았다. 기존 제품 소스와 앞선 보고서는 변경하지 않고 이 해설 파일을 추가한다.
