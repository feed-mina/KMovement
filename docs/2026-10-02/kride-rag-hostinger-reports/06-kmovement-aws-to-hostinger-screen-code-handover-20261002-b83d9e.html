KMovement AWS→Hostinger 화면·코드·배포 인수인계

현재 요청이 화면에서 어떤 컨테이너와 저장소를 지나가는지 추적하고, EC2에 묶인 항목만 Hostinger로 옮기는 순서를 정리했다. 이 문서는 이전 설계이며 실제 Hostinger 생성·배포·DNS 변경은 수행하지 않았다.

현재 판정: 조건부 이전 가능. Docker 기반 앱 계층은 그대로 옮길 수 있지만 PostgreSQL·ChromaDB·인증서·호스트 파일의 실제 백업 크기와 Hostinger VPS 사양이 아직 확인되지 않았다.

3줄 줄거리

1. 브라우저 요청은 Nginx가 Next.js, Spring Boot, FastAPI로 나누고 Redis·PostgreSQL·ChromaDB가 상태를 맡는다.
2. EC2를 Hostinger VPS로 바꿔도 외부의 RunPod·Supabase·Cloudinary·GCP·Firebase·지도/LLM 서비스는 그대로 남는다.
3. 새 서버를 병렬로 세운 뒤 데이터 복원, 내부 헬스체크, 임시 도메인 검증을 통과해야 DNS를 전환한다.

EC2만 바꾼다고 AWS 의존성이 0이 되지는 않는다. S3Service와 S3 자격증명은 별도 교체 대상이다.

화면에서 저장값까지 따라가는 구조

M1. 진입·TLS

받는 값: HTTPS 경로와 쿠키·SSE 연결.

처리: deploy/ec2/nginx.conf가 /api/, /kride-api/, /jobs/celery/, 나머지 화면을 서로 다른 프로세스로 전달한다.

Hostinger 영향: 도메인 DNS, 인증서, 80/443 방화벽, Nginx 설정을 새 VPS에서 먼저 준비한다. 외부 공개 포트는 80/443과 제한된 SSH만 허용하고 앱 포트는 호스트 내부로 제한한다.

검증: 임시 호스트명에서 화면 3개와 FastAPI health, SSE 응답을 확인한다.

M2. Next.js 화면

파일: subproject/SDUI/metadata-project/Dockerfile, next.config.ts.

처리: 빌드 시 공개 지도·Firebase 설정과 백엔드 주소를 넣고, 런타임에는 Spring/FastAPI 프록시를 사용한다.

Hostinger 영향: 이미지 자체는 재사용 가능하지만 새 도메인이 바뀌면 사이트 URL, OAuth 허용 도메인, CSP 연결 대상과 공유 링크를 함께 확인한다.

M3. Spring Boot 업무 API

파일: subproject/SDUI/SDUI-server, application.yml.

처리: 회원·로그인·SDUI 화면 정의·커뮤니티·여행 데이터·AI 중계·S3 presign을 처리한다.

저장: PostgreSQL이 영속 데이터, Redis DB 0이 토큰·캐시를 담당한다.

주의: 현재 운영 배포 스크립트는 sdui-db가 이미 존재한다고 가정한다. DB 생성·볼륨·백업 절차가 스크립트에 없으므로 실제 볼륨을 먼저 식별해야 한다.

M4. FastAPI·Celery AI 경로

파일: src/api/fastapi_server.py, rag_client.py, Dockerfile.worker.

처리: 추천·경로·RAG·RunPod 작업을 제공하고 Celery가 media·maintenance·beat 큐를 나눠 처리한다.

저장: Redis DB 1은 broker/result, ChromaDB는 호스트의 ~/kride-data/chroma_db, 임시 미디어와 beat 일정은 Docker 볼륨에 있다.

주의: Chroma 디렉터리와 Celery 볼륨은 애플리케이션 이미지에 포함되지 않는다.

M5. 데이터·파일 이전

반드시 백업: PostgreSQL dump, ChromaDB 디렉터리, study-materials, GCP/Firebase 자격 파일, 필요한 Celery 볼륨, Nginx/인증서 설정.

재생성 가능: Docker 이미지·빌드 캐시·Hugging Face 캐시는 백업보다 새 서버 pull/rebuild가 안전하다.

S3 분기: 1차 이전에서는 S3를 유지하면 앱 호스트 이동 위험을 줄일 수 있다. AWS 완전 종료는 S3 호환 저장소 추상화, 기존 객체 복사, presigned URL·암호화·삭제 수명 검증을 별도 단계로 수행한다.

M6. CI/CD와 복구

현재: GitHub Actions가 Docker Hub에 네 이미지를 올리고 AWS SSH 자격으로 원격 스크립트를 실행한다.

제안: Hostinger 공식 deploy action 또는 Hostinger 전용 SSH 비밀 이름으로 워크플로를 분리한다. 기존 AWS 워크플로는 첫 성공 직후 삭제하지 말고 수동 복구용으로 잠시 보존한다.

완료 증거: 새 서버 컨테이너·페이지·API·SSE·DB 건수·Chroma 컬렉션·업로드/다운로드 검증, DNS 전환 후 외부 검증, 롤백 리허설.

Before / After

현재 · 코드 기반 재구성

AWS EC2 단일 호스트

GitHub Actions → AWS SSH → Docker 컨테이너와 호스트 Nginx

PostgreSQL 컨테이너·Chroma 호스트 폴더·자격 파일 위치가 서버에 묶여 있다.

배포 전 최소 4GiB 여유 공간을 요구하며 이미지 정리 후 재기동한다.

개선 예상 모형 · 미배포

Hostinger 병렬 호스트

GitHub Actions → Hostinger deploy/SSH → 동일 Docker 서비스

명시적 영속 볼륨, 백업·복원 문서, 내부 전용 포트, 커밋 SHA 이미지 태그를 사용한다.

임시 도메인 검증 뒤 DNS만 전환하고 AWS는 롤백 창 동안 유지한다.

아직 알아내야 하는 값

  • 미확인 Hostinger VPS의 실제 vCPU·RAM·디스크·리전과 현재 사용 가능한 여유 공간
  • 미확인 EC2의 24시간·7일 CPU/RAM/디스크·트래픽 최고치와 Docker 이미지/볼륨 크기
  • 미확인 sdui-db의 실제 볼륨, DB별 크기, 마지막 백업·복원 성공 시각
  • 미확인 ChromaDB 컬렉션·문서 수와 파일 복사 중 쓰기 정지 방법
  • 미확인 AWS S3를 유지할지, 별도 S3 호환 저장소로 옮겨 AWS를 완전히 종료할지
  • 미확인 DuckDNS TTL, OAuth·Kakao·Google·Firebase의 허용 도메인/리다이렉트 등록 상태
