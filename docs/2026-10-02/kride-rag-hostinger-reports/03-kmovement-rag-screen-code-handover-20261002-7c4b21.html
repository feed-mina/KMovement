핵심: 화면 입력은 의도에 따라 QA·추천·일정으로 갈라집니다. QA에는 거리 임계값이 있지만 출처가 화면까지 오지 않고, 일정은 근거 POI가 0건이어도 생성 호출을 계속할 수 있습니다.

대상: feed-mina/KMovement @ 4cfedf6 · 실제 운영 배포 경로는 미확인

H1. 입력과 의도 분기

사용자 행동: 제안 문구를 누르거나 질문을 전송합니다.

담당: KrideChatComponent → useKrideChatStream.send() → classifyIntent().

받는 값: 질문과 브라우저에 저장된 아티스트·지역·목적·기간·예산.

처리: “일정/코스/여행 계획”은 일정, “추천/맛집/관광지/촬영지”는 추천, 나머지는 QA입니다.

화면 결과: QA는 스트리밍, 나머지는 한 번에 응답을 받습니다.

useKrideChatStream.ts

H2. Spring 중계

요청: POST /api/v1/kride/chat 또는 /stream.

처리: KrideChatController가 API 키·사용량을 확인하고 사용자 문맥을 붙입니다. KrideChatService가 의도를 다시 판별해 FastAPI 경로를 선택합니다.

반환: ChatQueryResponse는 intent, reply, pois, recommendationText, itinerary만 가집니다.

영향: QA 검색 문서·점수·출처가 FastAPI에 있어도 현재 DTO에서 화면으로 전달할 자리가 없습니다.

Controller · Service · Response DTO

H3. QA 검색과 답변

담당: search_chat_context()가 PDF와 네 종류 POI 컬렉션을 각각 조회합니다.

입력: 질문 임베딩, 컬렉션마다 top_k=3.

처리: ID·이름·텍스트 앞부분으로 중복을 제거하고 거리 오름차순으로 합칩니다. distance <= 0.25만 생성 문맥으로 사용합니다.

빈 결과: 모델 프롬프트에 참고 자료 없음 문구를 넣고 특정 장소·맛집 질문이면 정해진 거절 문구를 요구합니다. 코드 수준 조기 종료는 아닙니다.

반환: 생성 문장만 반환하며 검색 문서와 점수는 사라집니다.

rag_client.py · fastapi_server.py

H4. 추천 검색

담당: search_pois_by_purpose(), GraphRAG 보강, generate_recommendation_text().

처리: 목적별 컬렉션을 벡터 조회한 뒤 지역을 애플리케이션 코드에서 후처리합니다. GraphRAG 결과와 합치고 중복을 제거합니다.

주의: 이 경로에는 QA의 distance <= 0.25가 없습니다. 메타데이터 where 필터도 검색 호출에 확인되지 않습니다.

반환: POI와 추천 문장. 모델에는 “목록에 없는 장소를 언급하지 말라”고 지시하지만 결과 검증기는 확인되지 않았습니다.

H5. 일정 생성

처리: ChromaDB·GraphRAG·Supabase 대체 경로를 합치고, 거리 순서로 묶은 POI를 생성 모델에 전달합니다.

근거 없음: POI가 0개면 로그를 남기고 poiGrounded=false를 응답에 넣지만 generate_itinerary() 호출은 계속합니다.

화면 위험: 프런트는 장소가 하나라도 생성되면 성공으로 볼 수 있고, poiGrounded를 차단 조건으로 사용하지 않습니다.

수정 영향: 생성 전 차단, 응답 DTO, 프런트 상태를 함께 변경·시험해야 합니다.

H6. 별도 Kaggle 경로

담당: kaggle/kaggle_server.py의 /api/chatbot.

처리: 질문 변형, 여러 컬렉션 검색, CrossEncoder 재정렬, 상위 10개 문맥을 사용합니다.

다른 계약: sources와 pois를 반환하지만 최소 재정렬 점수 기준은 확인되지 않았습니다.

미확인: 이 서버가 현재 사용자 화면에서 호출되는 운영 경로인지 증명되지 않았습니다. 메인 FastAPI와 섞어서 설명하면 안 됩니다.
