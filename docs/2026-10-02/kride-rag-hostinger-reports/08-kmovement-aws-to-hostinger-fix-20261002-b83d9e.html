KMovement AWS→Hostinger 이전 실행안

EC2용 배포 자동화를 Hostinger 전용 경로로 분리하고, 상태 없는 앱과 상태 있는 데이터를 따로 이전해야 한다. 이 문서는 수정 위치·검증 증거·에이전트 요청문을 제공하지만 코드 수정과 실제 배포는 아직 하지 않았다.

결론: 앱 컨테이너 이동은 직접 대응 가능하다. 단, PostgreSQL/Chroma/호스트 파일 백업, Hostinger 용량, S3 처리 방침이 확정되기 전에는 cutover를 보류한다.

3줄 줄거리

1. 현재 EC2 워크플로와 스크립트를 복제하지 말고 Hostinger용 compose·workflow로 분리한다.
2. PostgreSQL·ChromaDB·호스트 bind·Docker volume을 명시적으로 백업하고 복원 증거를 남긴다.
3. 임시 도메인 E2E와 롤백 리허설을 통과한 뒤 DNS를 전환하고 AWS는 관찰 기간 후 종료한다.

클릭형 수정 지도

P1. CI/CD 공급자 분리

현재 문제: deploy-ec2.yml은 AWS 이름의 host/user/key와 /home/ubuntu 경로에 결합돼 있다.

사용자 직접 할 일: Hostinger hPanel에서 API key·VM ID 또는 전용 SSH 사용자/키를 준비하고 값은 GitHub Secrets에만 저장한다.

수정 제안: deploy-hostinger.yml을 새로 만들고 기존 AWS workflow는 수동 전용으로 보존한다. 공식 hostinger/deploy-action@v1을 택할 경우 compose가 배포 단위가 되도록 한다.

증거: push가 아닌 수동 dry path에서 대상 VM·프로젝트 이름·compose 경로가 확인되고 비밀값은 로그에 노출되지 않는다.

P2. 운영 Compose 만들기

현재 문제: EC2 배포는 긴 docker run 목록으로 서비스와 비밀을 조립하며 DB는 이미 존재한다고 가정한다.

수정 제안: Next.js, Spring, FastAPI, Redis, media/maintenance/beat, PostgreSQL을 하나의 운영 compose 또는 역할별 두 compose로 정의한다. 앱 포트는 127.0.0.1 또는 내부 network에만 바인드하고 Nginx/Traefik만 공개한다.

증거: docker compose config에 미치환 값이 없고, named volume·healthcheck·restart·log rotation이 명시된다.

P3. 데이터 이전

현재 문제: PostgreSQL 컨테이너와 볼륨 생성이 운영 배포 스크립트 밖에 있고 Chroma는 호스트 폴더, study 자료와 자격 파일도 호스트 경로다.

수정 제안: 데이터 목록·크기·소유권·해시를 먼저 기록한다. PostgreSQL은 논리 dump와 복원 검증, Chroma는 쓰기 정지 후 아카이브/해시, bind 파일은 최소 권한으로 복사한다.

증거: DB 핵심 테이블 수, Chroma collection/doc 수, 파일 해시, 로그인·쓰기·검색 프로브가 전후 일치한다.

P4. S3 완전 제거 여부

현재 문제: S3Config/S3Service가 AWS SDK·bucket·presigned URL에 직접 의존한다.

권장: 1차 compute 이전에서는 S3를 유지한다. 2차에 ObjectStoragePort 같은 경계를 두고 S3 호환 공급자 또는 Hostinger VPS의 별도 MinIO를 평가한다. MinIO를 같은 VPS에 둘 경우 앱 장애와 파일 장애가 한 서버에 모이는 위험을 문서화한다.

증거: 업로드·다운로드·만료 URL·암호화·삭제·기존 객체 접근을 고정 평가셋으로 통과한다.

P5. DNS 전환과 롤백

현재 문제: OAuth redirect, Kakao/Google/Firebase 허용 도메인, CSP, site URL이 현재 도메인과 연결돼 있다.

수정 제안: 동일 도메인을 유지하고 IP만 바꾸되 사전 TTL을 낮춘다. 임시 하위 도메인에서 인증·SSE·지도·업로드를 검증한다. 전환 직전 쓰기 정지와 최종 DB delta를 적용한다.

증거: 외부 네트워크 E2E, DNS 응답, 인증 콜백, 오류율·지연, AWS로 되돌리는 리허설 기록.

P6. 관찰과 AWS 종료

현재 문제: 새 서버가 켜졌다는 사실은 운영 이전 완료가 아니다.

수정 제안: CPU/RAM/disk/inode/traffic, 컨테이너 restart, 5xx, 큐 길이, DB 연결, Chroma/Supabase/TourAPI 품질 경고를 관찰한다. Hostinger 스냅샷은 전체 복구용이고 앱별 DB 복구를 대신하지 않는다.

증거: 합의한 관찰 기간 무장애, 백업 복원 시험, AWS 종료 체크리스트 승인.

에이전트에게 그대로 전달할 요청문

목표: KMovement의 현재 AWS EC2 앱 호스팅을 Hostinger VPS로 병렬 이전하고, 데이터·인증·RAG·Celery 검증을 통과한 뒤 DNS cutover가 가능한 PR을 만든다.

대상: feed-mina/KMovement main. 현재 근거는 .github/workflows/deploy-ec2.yml, deploy/ec2/deploy.sh, deploy/ec2/nginx.conf, Next.js metadata-project, Spring SDUI-server, src/api FastAPI/Celery다.

확인된 사실:
- EC2 호스트에는 Next.js, Spring Boot, FastAPI, Redis, Celery worker/maintenance/beat, host Nginx가 함께 동작한다.
- PostgreSQL sdui-db는 배포 스크립트가 생성하지 않고 기존 컨테이너를 전제로 한다.
- ChromaDB는 호스트의 kride-data/chroma_db bind mount이며 Celery 임시·beat 데이터는 Docker volume이다.
- RunPod, Supabase, Cloudinary, GCP Document AI, Firebase, 지도·TourAPI·LLM은 외부 의존성으로 남는다.
- S3Service는 AWS SDK와 presigned URL을 사용하므로 EC2 이전만으로 AWS 의존성이 사라지지 않는다.

미확정 가설:
- Hostinger VPS 사양이 현재 24시간/7일 최고 사용량과 배포 시 필요한 디스크 여유를 수용한다.
- sdui-db의 실제 volume과 최신 복구 가능한 백업이 식별된다.
- 동일 도메인을 유지하면 OAuth·지도·Firebase 설정 변경은 최소화할 수 있다.

맡길 범위:
1. 읽기 전용 inventory 보고서를 먼저 작성한다. 비밀값은 출력하지 않는다.
2. deploy/hostinger 운영 compose, proxy 설정, GitHub Actions workflow, backup/restore/cutover/rollback runbook을 PR로 만든다.
3. 운영 DNS·AWS·Hostinger에는 배포하지 않는다. 실제 cutover는 별도 승인까지 금지한다.
4. 1차 PR에서는 S3를 유지한다. AWS 완전 제거용 object storage adapter는 별도 PR 제안으로 분리한다.

완료 기준:
- docker compose config와 정적 테스트 통과
- 모든 서비스의 healthcheck, 내부 전용 포트, named volume, log rotation, 커밋 SHA image tag 명시
- PostgreSQL/Chroma/bind/volume별 백업·복원·대조 절차와 실패 시 AWS 복귀 절차 포함
- 필요한 GitHub Secrets/Variables는 이름만 문서화하고 값은 노출하지 않음
- PR URL, 변경 파일 표, 미실행 항목, 실제 배포에 필요한 사용자 승인 목록 제공

완료 보고에서 받아야 할 증거

  • Hostinger 실제 사양과 AWS 24시간/7일 측정치 비교표
  • compose 렌더 결과와 컨테이너별 healthcheck 목록
  • PostgreSQL 핵심 테이블 건수·Chroma collection/doc 수·파일 해시 전후 표
  • 메인·K-pop·맛집·로그인·추천·SSE·업로드의 입력과 결과
  • DNS 전환 전/후 IP, 인증서, OAuth callback, 5xx·지연 관찰
  • 실제 롤백 리허설 시간과 AWS 재개 확인
중단 기준: 백업 복원 실패, DB/Chroma 수 불일치, Hostinger 디스크 바닥 미충족, 인증 콜백 실패, SSE 단절 중 하나라도 있으면 DNS 전환을 보류한다.
