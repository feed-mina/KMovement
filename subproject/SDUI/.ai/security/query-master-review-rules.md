# query_master SQL 등록 검토 규칙

작성: 2026-11-15 · 대상: `query_master` 표에 SQL을 새로 넣거나 바꾸는 모든 사람

## 왜 필요한가

`/api/execute/{sqlKey}`는 로그인 없이도 부를 수 있는 공개 창구입니다(`SecurityConfig`). 이 창구는 `query_master`에 저장된 SQL을 그대로 실행하므로, **SQL을 등록하는 순간 그 SQL이 인터넷에 공개되는 것과 같습니다.** 코드 리뷰를 거치지 않고 DB에 바로 들어가는 값이라 아래 규칙을 사람이 확인해야 합니다.

## 이미 코드가 막아 주는 것 (`QueryParameterPolicy`, `CommonQueryController`)

| 막는 것 | 방법 |
|---|---|
| 요청이 사용자 번호를 바꿔치기 | `userSqno`, `userId`는 요청에서 받으면 거절하고, 서버가 로그인 정보로 채운다 |
| 선언하지 않은 값 끼워 넣기 | `param_mapping`에 없는 이름은 거절, SQL에 없는 이름이 선언돼 있어도 설정 오류 |
| 문자열 이어 붙이기 공격 | 모든 값은 `:이름` 자리표시자로 바인딩한다 |
| 너무 큰 값 | 문자 2,000자, 목록 100개, JSON 20,000자 상한 |
| 권한 | `query_master`의 역할 설정으로 화면별 권한 검사 |

## 등록 전에 사람이 확인할 것

1. **쓰기 SQL(INSERT·UPDATE·DELETE·MERGE·DDL)은 기본으로 등록하지 않는다.** 꼭 필요하면 아래를 모두 만족해야 한다.
   - 대상 행을 `user_sqno = :userSqno` 조건으로 **본인 행만** 고친다.
   - 역할 설정으로 로그인 사용자 이상만 실행되게 한다.
   - 같은 기능을 일반 API(Controller → Service → Repository)로 만들 수 없는 이유를 PR이나 변경 기록에 남긴다.
2. **읽기 SQL도 공개 범위를 확인한다.** 비공개·미승인 행(`approved_yn <> 'Y'`, `visibility <> 'PUBLIC'`)이 섞여 나오지 않는지, 개인정보 열(이메일, 전화, 토큰 등)을 고르지 않는지 본다.
3. **`:userSqno`를 쓰는 SQL은 로그인 필수가 된다.** 비로그인 화면에서 쓸 SQL이면 사용자 조건을 넣지 않는다.
4. **`LIMIT`을 둔다.** 목록 SQL은 한 번에 돌려줄 최대 행 수를 정한다.
5. **`sql_key`가 `kpop_`로 시작하면** 바꾼 순간 K-POP 캐시가 비워진다(`PostgresCacheListener`). 대량 변경은 사용이 적은 시간에 한다.
6. **변경 기록을 남긴다.** 운영 DB에 직접 넣을 때도 넣은 SQL 원문을 저장소의 마이그레이션 또는 `.ai` 기록으로 남긴다.

## 검토 체크리스트 (복사해서 사용)

- [ ] 읽기 전용인가? 쓰기라면 1번 조건을 모두 만족하는가?
- [ ] 비공개·개인정보 열이 나오지 않는가?
- [ ] 모든 값이 `:이름` 바인딩이고 `param_mapping`·`required_params`가 SQL과 맞는가?
- [ ] 목록이면 `LIMIT`이 있는가?
- [ ] 역할 설정이 화면 공개 범위와 맞는가?
- [ ] SQL 원문을 기록했는가?
